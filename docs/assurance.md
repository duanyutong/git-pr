# Behavioural assurance

The assurance programme supplements line coverage with independent contracts, generated inputs, real-Git observations, bounded workflow transitions, deliberate defect reintroduction, mutation analysis and semantic fuzzing.
The [contract inventory](behavioural-contracts.md) specifies the authoritative expectations, permissible normalisation, executable assertions and campaign bounds.
These methods establish distinct forms of evidence and shall not be reduced to a single coverage percentage.
No successful finite campaign establishes the absence of all defects.

## Commands and prerequisites

Run commands from the repository root after the normal [development setup](development.md).
The declared `prek` hooks provision cargo-mutants `27.1.0` and cargo-fuzz `0.13.2` in their managed environments; no additional repository-specific executable path is required.
The property-testing dependency and its transitive graph are resolved by the root `Cargo.lock`, while the independent fuzz workspace has its own `fuzz/Cargo.lock`.
Ordinary property tests and retained fuzz replay use the supported stable compiler.
Coverage-guided fuzzing requires `nightly-2026-10-14` and a supported C++ compiler, as specified by the [Rust Fuzz Book](https://rust-fuzz.github.io/book/cargo-fuzz/setup.html).

```sh
just assurance
just mutants
just mutants origin/main
just fuzz-smoke
just fuzz 60 20261015
just coverage-branches
```

`just assurance` runs the generated property and native contract suites, the known-defect sensitivity experiments and deterministic fuzz corpus replay.
`just mutants` analyses the complete declared critical function scope; an optional revision argument intersects that scope with changes relative to the resolved commit.
`just fuzz-smoke` executes retained semantic inputs and reproducible generated bytes without requiring nightly instrumentation.
`just fuzz SECONDS SEED` runs each of the three instrumented fuzz targets for its own time budget, excluding compilation; the defaults are 60 seconds and seed `20261015`.
`just coverage-branches` requires complete branch outcomes within the independently measured application policy unit scope under the pinned nightly compiler.
The existing `just check`, `just coverage`, `just parity` and `just backends` gates remain mandatory acceptance requirements.
Assurance commands do not submit against the developer's working stack, copy personal credentials into fixtures or contact live submission targets.

## Generated properties and workflow campaigns

The property suite uses [Proptest](https://proptest-rs.github.io/proptest/intro.html) with an ordinary budget of 128 cases for each of seventeen properties and a fixed default seed of `5138697615354058066`.
`PROPTEST_CASES` and `PROPTEST_RNG_SEED` override those defaults, and `GIT_PR_ASSURANCE_CASES` controls the native generated-ref sample count, ordinarily eight and bounded at 256.
The assurance wrapper rejects nonpositive case counts and records its effective input settings.
For example, the following command expands the generated campaigns while retaining known-defect and corpus validation:

```sh
PROPTEST_CASES=4096 PROPTEST_RNG_SEED=20261015 GIT_PR_ASSURANCE_CASES=64 just assurance
```

The unit properties construct independent footer expectations, framed Git records, stack positions and human description sections, rather than relying solely upon parser and serialiser agreement.
The native suite asks actual Git to validate ref syntax, resolve remote symbolic refs and push destinations, publish to disposable repositories and observe the resulting identities.
It also compares the shared in-memory fixture's selected-remote observations against actual Git.
The bounded workflow model enumerates 125 ordered three-action sequences, 22 before-effect or lost-acknowledgement fault configurations and eighteen remote base or lifecycle refusal configurations.
The precise dimensions and limits are specified in the [contract inventory](behavioural-contracts.md#bounded-state-transitions-and-failure-positions).
Completed remote effects remain part of the expected model after uncertainty; the tests require reconciliation rather than fictitious universal rollback.

Property failures undergo bounded shrinking and seed persistence under `proptest-regressions/`.
Retain the minimised behavioural example as an explicit regression as well as retaining its generated seed, because dependency or generator changes may alter seed interpretation.
Generated-ref sampling and bounded transition enumeration provide evidence for their stated dimensions; neither establishes exhaustive coverage of all valid refs or all possible operation histories.

## Known-defect sensitivity

The sensitivity gate copies only explicitly allowlisted build and test inputs, including applicable new source files, into a disposable source tree.
Path containment checks exclude escaping paths and the developer's Git metadata; unrelated personal files and credentials are outside the allowlist.
It records SHA-256 source identities, executes each exact regression against the unmodified copy, reintroduces one reviewed faulty decision and requires an actual assertion failure in that same regression.
Stale mutation anchors, compilation failure, timeout, an empty test selection or an unrelated process failure shall not count as detection.
The original source is restored between experiments, and the developer's source tree is never modified by these experiments.

| Defect class | Deliberately restored decision | Required regression |
| --- | --- | --- |
| Fetch and push destination confusion | Verify the fetch URL after a failed push instead of every resolved push URL. | `failed_publication_verifies_every_push_destination_instead_of_the_fetch_url` |
| One-character `Remote-Ref` rejection | Reject a nonempty one-character remote ref during trailer parsing. | `existing_single_character_remote_ref_is_published_without_rewriting` |
| Pipe-containing branch truncation | Split branch inventories at the first pipe instead of the final field separator. | `pipe_branch_is_synchronised_without_moving_the_checked_out_branch` |
| One-character trailer rejection | Reject a one-character non-`Remote-Ref` trailer and consequently discard the footer. | `single_character_tags_preserve_the_published_branch_and_label` |
| Ambiguous default branch discovery | Ask Git for an abbreviated symbolic target and interpret that abbreviation as an unambiguous remote branch. | `trunk_discovery_ignores_shadowing_local_branches_and_tags` |
| Duplicate trailer precedence reversal | Emit equal-key internal attributes in their current order, reversing their effective precedence on the subsequent parse. | `duplicate_trailer_winners_survive_rewriting` |

The first five classes concern previously corrected defects; the sixth was independently detected by the new generated trailer assertions.
A successful sensitivity run demonstrates that these six exact defects are detected by the named assertions.
It does not establish that every conceivable variation of those defects has been enumerated.

## Mutation analysis

[cargo-mutants](https://mutants.rs/) introduces small production changes and executes the selected tests to determine whether their assertions detect those changes.
The reviewed file and name filters in [.cargo/mutants.toml](../.cargo/mutants.toml) prioritise trailer interpretation, literal ref validation, trunk protection, selection, ref recovery and submission policy.
Their source scope comprises `src/model/trailers.rs`, `src/git/policy.rs`, `src/stack/selection.rs` and `src/submission/policy.rs`; directory reorganisation does not expand or reduce that behavioural scope.
It runs locked library unit tests and applies bounded build and test deadlines, with a minimum test allowance of 60 seconds.
The actual generated inventory is authoritative for the executed scope and may additionally include tool-generated structure-field changes within the selected files.
The declared filter alone shall not be represented as an exact count of examined functions or mutations.
Functions and mutation operators absent from the recorded inventory receive no implied mutation score.
The sole reviewed operator exclusion is justified below by the production caller contract; no broader function or safety decision is excluded merely to obtain a favourable result.

| Outcome | Interpretation and gate treatment |
| --- | --- |
| Caught executable mutant | The changed production behaviour caused a test failure and contributes detection evidence. |
| Unviable mutant | The artificial change could not build; it supplies no evidence that assertions detected changed executable behaviour and is reported separately. |
| Surviving executable mutant | The selected assertions failed to distinguish the changed behaviour; the gate fails pending investigation. |
| Timeout, execution failure or missing baseline | The result is inconclusive; the gate fails and retains the evidence. |
| No mutations in an explicitly requested changed scope | The report records that no changed mutations were generated; it does not claim a perfect score or full-scope execution. |

The gate requires a successful unmodified baseline, at least one detected executable mutation in a nonempty campaign and no unresolved outcomes.
Any equivalent or unreachable mutation requires an explicit, narrowly justified review; the current gate does not silently waive surviving executable changes.
Report caught, unviable and unresolved counts together with the function scope, operators, exclusions, dependency versions and execution budget.
Do not describe the result as a whole-application mutation score.

An optional base revision is resolved to a commit identity and retained with the exact diff supplied to cargo-mutants.
PR analysis may therefore test only changed lines within the declared critical scope, while scheduled analysis executes the complete inventory produced by those filters.
A passing changed-scope run supplies no evidence for unchanged functions omitted by that intersection.

### Reviewed equivalent operator

The initial campaign retained the surviving mutation `src/selection.rs:293:77: replace < with <= in slice_start` for independent review.
The function now resides in `src/stack/selection.rs`; the historical mutation identity above remains unchanged as recorded evidence.
The reviewed exclusion matches only the current source path, function and operator replacement, permitting line and column numbers to change without excluding other mutations.
It shall be reported as an excluded equivalent operator, not as a caught executable mutation.

The production caller, `State::discover` in `src/submission/state.rs`, obtains the depth map from `Git::observe_stack`.
That observation obtains depths from `snapshot::linear_depths`, which verifies the complete single-parent path before assigning a unique rank to each commit identity and its base.
An unverified path produces no ranks rather than ambiguous or duplicate ranks.
Within `slice_start`, the depth comparison is reached only after the function has established that the requested base is absent from the visible stack.
Consequently, a visible candidate with a known verified rank cannot have the same rank as that absent base; candidates without ranks fail the `is_some_and` check under either operator.
For every input admitted by these caller contracts, `<` and `<=` therefore select the same visible position or the same absence result.

Supplying a fabricated map in which distinct identities share a rank would violate the verified-depth contract and would not demonstrate a supported behavioural difference.
The [generated ancestry property](../src/tests/unit/properties.rs) constructs unique verified ranks across filtered stacks and asserts the independently expected range boundary.
Changes to either caller, rank construction or the accepted depth-map contract require renewed review of this equivalence and removal of the exclusion if equality becomes reachable.

## Semantic fuzzing and reproduction

The independent [fuzz workspace](../fuzz/README.md) compiles the actual production trailer, structured snapshot, description and model sources without adding fuzz dependencies to the released executable.
Its `trailers`, `snapshots` and `descriptions` targets exercise arbitrary bytes interpreted as text and independently generated valid structures.
Their semantic oracles require metadata preservation, duplicate precedence, exact framed records, conservative delimiter handling, preservation of human sections and stable repeated rendering.
The campaign bounds inputs at 4,096 bytes and valid snapshot expansion at five records; instrumented execution additionally bounds individual inputs at ten seconds and memory at 2,048 MiB.

Stable replay executes every reviewed input under `fuzz/seeds/` and 256 newly generated byte inputs per target using the recorded seed.
Generated bytes are retained separately from the reviewed corpus, and each input path is logged before execution.
An assertion failure is directly reproducible by invoking the built replay executable:

```sh
fuzz/target/debug/replay descriptions PATH_TO_INPUT
```

Instrumented campaigns retain their evolving corpora and libFuzzer counterexample artefacts separately from the reviewed inputs.
A crash, semantic assertion failure, unavailable required tool or timeout shall remain a failed campaign.
Minimise a failing input using the [cargo-fuzz reproduction and minimisation guidance](https://rust-fuzz.github.io/book/cargo-fuzz/guide.html), retain its exact bytes under the appropriate `fuzz/seeds/` directory and add an independent deterministic regression before accepting its production correction.
Binary seeds, malformed framing and intentional carriage returns shall not be rewritten by text-formatting hooks.
An early semantic replay exposed a description fixed-point defect for the exact existing text `human\r`: appending a newline separator manufactured CRLF which was only normalised on the next invocation.
A further counterexample containing two adjacent carriage returns established that a single replacement pass could leave an overlapping CRLF sequence and fail again on repetition.
The specified correction canonicalises every run of one or more carriage returns immediately preceding LF to a single LF, in both observed descriptions and newly composed output, including initial message or template text and manufactured separators.
Carriage returns outside such a run remain unchanged, and the normalisation is a fixed point on its first application.
Byte-exact seeds and deterministic regressions retain this distinction; their presence does not broaden the contract to arbitrary carriage-return removal.

## Continuous enforcement

The [ordinary CI workflow](../.github/workflows/ci.yml) retains macOS and Ubuntu acceptance and includes separate Ubuntu boundary jobs for `assurance`, `mutants` and `coverage-branches`.
For a pull request, mutation execution intersects the declared critical function scope with changes relative to the PR base commit; push and manual ordinary CI execution use the complete declared scope.
The [scheduled assurance workflow](../.github/workflows/assurance.yml) runs daily at 04:23 UTC and also permits manual dispatch.
Its independent Ubuntu jobs execute 4,096 cases per generated property with 64 native ref samples, the complete critical mutation scope, 300 seconds of instrumented fuzzing per target and the complete unit branch gate.
The workflow run identifier determines the property seed, and its value modulo 2³² determines the libFuzzer seed.
Ordinary boundary jobs and scheduled assurance jobs each have a 120-minute deadline.
Both workflows retain assurance reports, fuzz evidence and Proptest regression seeds as artefacts even when their corresponding jobs fail.
Scheduled exploration supplements ordinary acceptance and does not imply that an unexecuted local or PR campaign passed.

## Unit branch coverage

Branch instrumentation uses the pinned nightly compiler and its matching LLVM tools component; the supported stable compiler remains authoritative for ordinary acceptance.
Install the instrumentation components before invoking the branch recipe:

```sh
rustup toolchain install nightly-2026-10-14 --profile minimal --component llvm-tools-preview
just coverage-branches
```

The collector executes the application unit suites alone and applies the declared policy-module exclusions, without counting native or differential integration execution towards those branch outcomes.
Its build and profile storage resides in `target/branch-coverage/`, isolated from ordinary coverage collection.
JSON, HTML, compiler identity, command logs and totals reside under `target/validation/assurance/branches/`.
The gate requires nonempty integer branch counters, equality between covered and total outcomes, and zero uncovered outcomes; a rounded percentage is insufficient.
A branch percentage concerns observed decision outcomes within that scope and compiler instrumentation; it does not establish all input combinations, all paths or correctness of the associated assertions.

The initial branch review supplied focused assertions for diagnostic-bearing configuration failures, non-exhausted or unspecified-reset quotas, malformed GraphQL error envelopes, secondary-rate wording, contradictory merged observations and conservative stack-schema fallback.
These observable cases reside in [the focused mutation and boundary assertions](../src/tests/unit/mutations.rs).
Repeated records for generic instantiations shall be assessed together before interpreting an individual zero count as an uncovered source decision.
The completion review removes only demonstrably redundant conditions: CLI positional and separator handling already prevents an empty flag name, complete observation decoding already rejects PR number zero, and explicit selection resolution already supplies a commit identity rather than the literal `HEAD`.
The private PR reconciliation interface no longer carries a Boolean whose sole production caller always supplied `false`; observed PR identity and creation state retain authority over lookup, creation and update decisions.
The publication selection guard remains in place and rejects a changed selected index even when the selected count remains constant.
Additional defensive assertions exercise pattern-only configuration reads, anomalous Git configuration output, empty observed Jujutsu change identities and cached all-state lookup of a closed PR.
The follow-up assertions additionally exercise a changed PR number during description recovery, non-prefix native membership with an agreeing base, and a commit-association 404 without the missing-commit diagnostic.
`content_recovery_never_replays_an_update_onto_a_replacement_pr_number` models a completed update followed by closure and replacement on the same head before acknowledgement; recovery preserves the replacement's title and human notes without replaying the mutation.
`inserting_a_middle_pr_rebuilds_native_membership_without_dropping_existing_members` supplies an already correctly based middle PR whose insertion requires rebuilding membership, and verifies retained identities, human content and the complete resulting member list.
`commit_association_access_failures_propagate_without_caching_absence` distinguishes HTTP 401 and generic 404 access or resource failures from GitHub's explicit missing-commit response, propagates their diagnostics without waiting and requires a fresh read on the next lookup.
These cases establish the specified decisions for their concrete observations; they do not exhaust concurrent schedules, arbitrary server failures or all combinations of native topology changes.
No fabricated state, weakened assertion or broad coverage exclusion is warranted merely to increase the reported percentage.

## Evidence and interpretation

Generated contract and sensitivity reports reside under `target/validation/assurance/`, including effective generation settings, commands, statuses, elapsed durations, source digests and exact defect edits as applicable to each gate.
Mutation evidence resides under `target/validation/assurance/mutants/`, including the tool identity, diff where applicable, command log and cargo-mutants outcomes.
Branch evidence resides under `target/validation/assurance/branches/`, with the scope and instrumentation limits specified above.
Fuzz reports, logs, generated inputs, corpora and artefacts reside under `target/validation/fuzz/`, with seeds, compiler identity, source hashes and ordered corpus digests.
The reports preserve unsuccessful and inconclusive attempts; a later successful attempt does not retroactively convert an earlier failure into detection evidence.

Line coverage establishes whether instrumented executable lines ran, whilst generated tests explore combinations, native tests check external contracts, mutation tests assess assertion sensitivity and fuzzing explores inputs under a finite budget.
Branch instrumentation, where available, measures decision outcomes separately and does not establish complete interaction coverage.
Record each metric with its scope and executed budget, and inspect retained failures before deciding whether the application, its contract or its test oracle requires correction.
