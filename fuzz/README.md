# Semantic fuzzing

This independent Cargo workspace compiles the application's actual trailer, structured Git snapshot, managed-description and commit-model source files.
It neither publishes additional application APIs nor introduces fuzz dependencies into the released executable.
The harness includes the production `src/model/mod.rs` directly, allowing Rust's ordinary child-module resolution to compile the same model sources in both workspaces.
Its crate-level trailer alias refers to that model module's `trailers` child; the snapshot and description harnesses therefore exercise the production trailer implementation rather than a copy.

The `trailers`, `snapshots` and `descriptions` targets each exercise arbitrary UTF-8 replacement text and independently constructed valid structures.
The trailer oracle requires normalised key/value grammar, retention of unknown metadata, one-character values, duplicate winner preservation and serialised metadata preservation.
The snapshot oracle requires exact commit, tree and parent identities, author information, messages, trailers and linear depth rankings for independently framed SHA-1 and SHA-256 records, and rejects truncated records.
The description oracle requires bounded output, valid delimiters, preservation of human text outside explicit managed markers, rejection of ambiguous markers and idempotence under an unchanged footer.
Inputs are bounded at 4,096 bytes; structured expansion is bounded by five snapshot records.
These contracts supplement crash detection without claiming exhaustive exploration.

Run `uv run scripts/fuzzing.py replay` with the repository's stable toolchain to build the locked harness, check its formatting and execute every retained input plus 256 reproducible generated inputs per target.
The fixed default seed is `20261015`; `--seed` and `--cases` select an alternative bounded campaign.
Generated bytes are retained separately from the reviewed corpus in `target/validation/fuzz/replay/generated/`.
Each batch logs the exact input path before execution, so an assertion failure is directly reproducible with `fuzz/target/debug/replay TARGET INPUT`.
Retained corpus files under `seeds/` are byte-exact fixtures, including intentionally incomplete framing and trailing carriage returns.
They shall not be normalised by text-formatting hooks.

Coverage-guided campaigns require cargo-fuzz `0.13.2`, the pinned `nightly-2026-10-14` toolchain and a supported C++ compiler.
Install them with `cargo install cargo-fuzz --version 0.13.2 --locked` and `rustup toolchain install nightly-2026-10-14 --profile minimal`.
The [Rust Fuzz Book](https://rust-fuzz.github.io/book/cargo-fuzz/setup.html) specifies the nightly requirement and supported platforms.
Run `uv run scripts/fuzzing.py campaign --seconds 60 --seed 20261015` to execute the three instrumented targets with AddressSanitizer and coverage guidance.
`GIT_PR_FUZZ_SECONDS` and `GIT_PR_FUZZ_SEED` set the corresponding defaults for scheduled execution.
The time budget applies separately to each target and excludes compilation.
Each individual input is subject to a ten-second timeout and a 2,048 MiB memory limit.

Every campaign writes a JSON report, complete command logs, ordered corpus digests, compiler identity, seed and elapsed duration beneath `target/validation/fuzz/`.
Instrumented runs additionally retain their evolving corpora and counterexample artefacts.
A crash, semantic assertion failure, unavailable tool or timeout returns an unsuccessful status and shall remain visible in CI evidence.
A failed campaign shall be minimised and its input retained under the corresponding `seeds/` directory before any production correction is accepted.
The [cargo-fuzz guide](https://rust-fuzz.github.io/book/cargo-fuzz/guide.html) describes reproduction and minimisation commands.
